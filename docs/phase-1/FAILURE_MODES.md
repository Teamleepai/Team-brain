## 1. Method, and why the severity scale is not the usual one

The conventional axis for severity is blast radius: how much data, how many users, how much money. Phase 1 has one user, no execution capability, and no financial surface, so that axis produces a document in which nothing is severe. It would also be wrong.

Phase 1's deliverable is not a briefing. It is **the founder's belief that the system's judgment is worth acting on** (`PRD.md` §4). That belief is the asset every later phase spends, and it is the thing failures here actually destroy. Severity is therefore graded by damage to trust and to the correctness of the trust signal, not by system impact.

| Severity | Meaning |
|---|---|
| **S1** | Plausibly ends adoption on its own, or destroys the integrity of the trust framework. Includes anything that makes the system confidently wrong, and anything that resets the 14-weekday exit window (`PRD.md` §9). |
| **S2** | Materially degrades correctness or usefulness. Survivable once; corrosive if repeated. Trust erodes cumulatively here. |
| **S3** | Noticeable, recoverable, self-evident to the founder as a system problem rather than a judgment problem. |
| **S4** | Cosmetic or internal. |

One classification rule follows from that framing and drives several rows below: **a failure the founder can see is less severe than the same failure hidden.** A briefing that fails to arrive is a bug. A briefing that arrives looking complete while one source has been dead for a week is a lie. The second is worse even though the first is more disruptive, and Phase 1's design should consistently prefer loud failure to quiet degradation.

A second rule concerns confidence. `PRD.md` A3 and `ARCHITECTURE.md` §7 both require low-confidence facts to be *excluded* rather than hedged. Anything that defeats that — bad ASR passing as certain, a collapsed memory record, a stale fact surviving supersession — is S1 by construction, because the product's core promise is that what it tells you is reliable enough to act on without checking.

## 2. The worst failure mode available: silence

`PRD.md` B1 and `ARCHITECTURE.md` §7 both name this, and it deserves the argument rather than the assertion.

Suppose generation fails at 6:40am and nothing is sent. From inside the system that is one failed job. From the founder's side, the inbox contains no briefing, and there are exactly two explanations available: the system broke, or the system ran and concluded that nothing warranted surfacing. **Those two states are indistinguishable from the outside, and they have opposite meanings.** One means "check your inbox yourself today." The other means "you're clear."

Every downstream consequence follows from that ambiguity. The founder either wastes the reconstruction effort the product exists to eliminate, or trusts the silence and misses whatever was in it. Worse, the ambiguity is self-concealing over time: after two or three silent days the founder stops distinguishing at all, stops looking for the briefing, and the sustained-use metric in `PRD.md` §5 fails for a reason nobody diagnoses as a defect. A trust-building product cannot afford a state whose meaning the user cannot determine, because trust is precisely the belief that absence of a warning means absence of a problem.

There is a sharper version. Silence does not merely fail to inform, it **actively misinforms**, because in a working system the null briefing is a meaningful signal. Once the product is trusted, no briefing reads as an all-clear. So a generation failure does not degrade the system to zero information; it degrades it to negative information, and does so at exactly the moment the system has the least ability to tell anyone.

The mitigation is the failure notice, and its properties matter as much as its existence:

- **It always sends.** The generation path is wrapped so that no failure mode — model outage, database unavailability, unhandled exception, timeout — exits without either a briefing or a notice. The notice path shares as little code with the generation path as possible, precisely so a bug in the latter cannot take out the former.
- **It says what happened and what to do.** "Briefing generation failed at 06:40; no data was lost; check your inbox and calendar directly today." Not "an error occurred." The purpose is to remove the ambiguity, which requires being explicit that the absence of items is not a finding.
- **It arrives in the delivery window,** not whenever someone notices. Which means the failure must be detected by a timeout rather than by the absence of a success signal.
- **A genuinely empty briefing is not silence.** If the system runs correctly and finds nothing worth surfacing, it sends a short briefing saying so. This is the one place `UX_PRINCIPLES.md`'s omit-empty-sections rule is deliberately overridden at the document level: omitting empty *sections* keeps a briefing readable, but omitting the entire *briefing* recreates the ambiguity.
- **Failure of the notice itself pages.** A failed failure notice is the silence case with a mitigation that believes it worked. It is the one Phase 1 condition that justifies waking someone.
- **The notice path is tested as carefully as the success path** (`TESTING_STRATEGY.md` §10). An untested mitigation for the worst failure mode is not a mitigation.

Residual risk, stated plainly: if the whole process or its host is dead, nothing sends the notice. Phase 1's answer is an external dead-man's-switch — a check independent of the application asserting that a briefing or a notice was recorded as delivered by a deadline each weekday, alerting if not. It is a small piece of work and it is the only thing that covers total-host failure.

## 4. The asymmetric trust dynamic

Every severity judgment above rests on one property of the primary persona, stated in `PRD.md` §6: **the founder extends trust readily on the first correct surprise, and withdraws it completely after two confident errors.**

That asymmetry is not a quirk to design around, it is the governing constraint. It has four consequences worth making explicit, because they justify design choices that would otherwise look excessive.

**Trust is cheap to gain and cannot be re-gained the same way.** One genuinely novel, correct item — a commitment from Tuesday's call that would have been missed — buys more credibility than three weeks of accurate-but-obvious briefings. But the reverse path is not symmetric. After two confident errors, subsequent correct briefings do not rebuild the belief, because the founder is now reading with verification, which costs more than not reading at all. The rational response to an unreliable assistant is to stop using it, and it is reached quickly.

**This is why the exit criterion is zero and why failing it resets the window** (`PRD.md` §9). A tolerance of one error per fortnight would be a defensible engineering target and a product mistake, because the second error is the one that ends adoption and a tolerance of one guarantees you eventually get two. The resetting window is not punitive bookkeeping; it encodes the fact that trust is measured in *unbroken* streaks. Two errors on days 3 and 12 of a 14-day window are not "93% accurate," they are two withdrawals of trust, and the window that follows them starts from a lower base than the first one did.

**Confidence must be calibrated, not maximized.** An item hedged into uselessness is a small loss. An item stated confidently and wrong is a large one. This asymmetry is the entire reason `PRD.md` A3 excludes low-confidence facts rather than hedging them: presenting a shaky claim with a caveat still spends the credibility of the briefing as a whole, because the founder does not maintain separate trust accounts for hedged and unhedged items. Omission costs one missed item. A confident error costs the product.

**Over-trust and under-trust are both failures, and they are not opposites to be balanced.** F1 and F2 are usually treated as ends of a dial where the goal is the middle. That framing is wrong here. The goal is *calibration*: the founder's confidence in each item should track the system's actual reliability on that item. Over-trust is dangerous because correctness makes verification feel unnecessary — the product earns its way into a position where its next error does maximum damage. Under-trust is dangerous because it is terminal and arrives fast. Both are addressed by the same mechanisms rather than by trading one off against the other: visible trust levels, one-click evidence, confidence-appropriate language, and exclusion rather than hedging. The system's job is not to be trusted as much as possible. It is to be trusted exactly as much as it deserves, which in Phase 1 means being unambiguous about what it does not know.

## 5. Graceful degradation

`TESTING_STANDARDS.md` requires graceful degradation rather than silent corruption. The governing rule, from §1: **degrade loudly and specifically.** A degraded briefing that says what it is missing preserves trust; a degraded briefing that looks complete spends it.

**One source is down or stale.** The briefing generates from the remaining sources and states the gap in a system-health line: "Slack has not synced since Tuesday 4pm; anything in channels since then is not reflected below." This is deliberately in the briefing rather than only on a dashboard, because the founder reads the briefing and nobody reads a dashboard at 6am. The affected sections are still rendered, since partial calendar and inbox data is worth far more than nothing, but no section implies completeness it does not have. If more than one source is stale, the notice moves to the top rather than the bottom. Nothing about this path is automatic recovery: `consecutive_failures` alerting fires in parallel so someone is fixing it, because a source that is stale for a week has become B1.

**The model API is unavailable.** Retry with backoff inside the delivery window. On exhaustion, prefer a **deterministic degraded briefing** over a failure notice: the calendar sections, open commitments already in the semantic layer, and items awaiting response are all queryable from memory without a model call, since they are stored facts rather than generated judgments. That briefing carries an explicit banner — "generated without prioritization; items are listed, not ranked" — because the synthesis is the missing part and claiming otherwise would be the confident-error failure at document scale. Only if the deterministic path also fails does the failure notice send. This ordering matters: the founder's worst outcome is silence, the second-worst is an unranked list presented as a ranked one, and the third-worst is an unranked list honestly labelled. Phase 1 should always land on the third.

**Memory retrieval returns nothing.** Two cases, and conflating them is itself a failure. If retrieval returns nothing because there is nothing — a genuinely quiet day, or early in a source's life — the briefing says so in one line, and that is a real briefing, not silence (§2). If retrieval returns nothing because retrieval is broken, that is detectable: the episodic layer is non-empty for the window while the semantic layer yields nothing, or retrieved-record count drops to zero against a nonzero baseline. That case sends a degraded briefing stating that memory retrieval failed and the founder should not read the absence of items as an all-clear. The system must never resolve this ambiguity in the reassuring direction. When it cannot tell which case it is in, it says the less comfortable thing.

**Distillation is behind.** The briefing reads from whatever the semantic layer contains and states the backlog when it exceeds one interval. Episodic data is not lost, so the gap closes on its own; the risk is a briefing implying it saw yesterday's calls when distillation has not reached them.

**Delivery fails.** Retry with backoff, then alert loudly. The briefing itself is already persisted, so nothing is lost and it can be re-sent. A generated-but-undelivered briefing is a recoverable state, and it should be recorded as one — `delivered_at` null with `generated_at` set is precisely the signal the deadline check looks for.

## 6. Residual risks and open questions

Named because a failure mode analysis that implies coverage is worse than one that admits gaps.

**Fixture-era adapters.** Every failure mode in category B involving real API behavior — pagination gaps, cursor expiry, auth refresh races, payload variance — is mitigated by tests that cannot exercise the condition. Live-credential validation per increment (`TESTING_STRATEGY.md` §12) is the actual mitigation and it has not happened yet. Until it does, B1, B5, and B6 are best understood as *identified* rather than *mitigated*.

**Omission-style prompt injection (D3)** has no reliable detector. It is the weakest-covered failure in Phase 1.

**Total host failure** defeats every in-application mitigation including the failure notice. The external deadline check is the only cover and it must exist before increment 1a is considered delivered, not after.

**The `dedupe_key` derivation is unspecified** (`DATA_MODEL.md` §13), so C1 and C2 are described precisely and mitigated only by a test suite whose subject does not yet exist.

**No voice provider is chosen** (`ADR-0006`), so B2's severity is asserted from general knowledge of ASR failure rather than from a measured error profile. The mitigation thresholds — the confidence floor, the diarization threshold — cannot be calibrated until there is a provider to calibrate against.

**Error flags depend on the founder noticing.** The primary correctness metric in `PRD.md` §5 is founder-reported. An error the founder does not notice does not reset the window, which means the exit criterion measures *detected* misleading recommendations. This is the honest limit of the metric and there is no better instrument available at one user. Worth stating so that a clean 14-day window is read as evidence rather than as proof.
